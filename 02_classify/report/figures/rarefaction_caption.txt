FULL CAPTION

Coverage of 22 established detections as their libraries are rarefied. The 5 runs
are wheat libraries already on scratch, so this costs no download; each carries several
detections and one Kraken2 report measures all of them at once. The reference set is each
run's db_v3 calls that cleared the published floors (score >= 0.7 and coverage >= 1%),
because those are the calls the project has committed to; measuring against db_v4's own
full-depth calls would be circular. Coverage is recomputed against db_v4 throughout, so
absolute values are not comparable with db_v3 -- the denominators differ -- while each
detection against itself across rungs is, which is the point.

DEPTH IS IN Gkmer, NOT Gb. At k=35 a read of length L yields L-34 k-mers, so k-mer yield
per base is (L-34)/L: 0.33 at 51 nt, 0.66 at 101 nt, 0.77 at 150 nt. Read length is
therefore worth a 2.3x factor independent of depth, and a library must be ranked on bases
x yield. Ranking on layout instead is plainly wrong: a paired-only filter would discard
301 single-end runs deeper than 2 Gb while keeping 311 paired runs under 1 Gb.

THE TWO ARMS are matched on Gkmer so the only difference between them is library SHAPE.
`native` subsamples the run as sequenced; `shallow` keeps one mate and truncates it to
51 nt, reproducing PRJDB7234. A gap between the arms at equal Gkmer isolates the
read-length effect, which is expected because --minimum-hit-groups 3 is harder to satisfy
with 17 k-mers per read than with 117.

WHAT THIS DECIDES. PRJDB7234 (1,557 runs) and PRJNA726716 (104 runs) sit at 0.019 and
0.036 Gkmer and are both rice, together 1,661 of the 2,784 rice runs. Whatever fraction
of detections survives at those rungs is the fraction of rice co-infections the pipeline
can see at all, and the quantity that collapses first is the NUMBER of pathogens per
sample -- which is the dependent variable. A depth cut-off is therefore a rice filter: at
0.2 Gb it removes 1,551 rice runs against 18 maize and 0 sorghum. The cut-off has to be
set on this curve and its cost to rice stated, not chosen by eye.

Only TWO projects fall entirely below 0.5 Gkmer and both are rice: PRJDB7234 (1,557
runs, median 0.019, max 0.214) and PRJNA726716 (104 runs, median 0.044, max 0.141).

READ LENGTH COSTS NOTHING BEYOND Gkmer, which was not the expected result. At matched
Gkmer the 51 nt single-end arm retains as many detections as the native paired arm
(5 vs 5, 8 vs 6, 9 vs 10, 12 vs 12 at the four shared rungs). The reasoning that
--minimum-hit-groups 3 would penalise a 17-k-mer read beyond its yield is NOT supported.
Gkmer is therefore a sufficient single statistic and a short-read library needs no extra
penalty, so one threshold on one number is defensible.

WHAT THE CURVE DOES NOT SAY. It uses the COVERAGE floor only; `score` needs detect.py's
whole-cohort accumulation fit, so retention here is an UPPER bound -- a detection failing
coverage would fail the pair too. Nested subsampling is not used: each rung is an
independent Bernoulli draw, so between-rung non-monotonicity is sampling noise and the
seed replicates at the two lowest rungs bound it. And these are wheat libraries; whether
a rice library of equal Gkmer behaves identically is an assumption, not a measurement,
because no deep rice library in the cohort carries established detections to rarefy.
